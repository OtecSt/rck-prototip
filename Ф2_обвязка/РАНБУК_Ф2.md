# Ранбук Фазы 2 — LLM-обвязка агента № 1 «Аналитик узких мест»

> Статус: v0.1 от 27.07.2026. Ядро: `../узкие_места.py` (Ф1, сдано).
> Спека: `../../Спеки/Спека_01_Узкие_места.md`. Роль: `../../Тестовый_агент_1_роль.md`.

## 1. Что такое Ф2 технически

Ф2 — это **цикл диспетчеризации**, а не новая программа. LLM — диспетчер и рассказчик,
Python-ядро — единственный счётчик. Правило из протокола № 7: агент ~70 % — детерминированный
код; LLM не считает ничего сама (риск арифметических галлюцинаций), только вызывает
инструменты и объясняет с цитатами.

## 2. Цикл одного запуска (пошагово)

```
Шаг 0. РОЛЬ: движок читает Тестовый_агент_1_роль.md → границы: только диагностика,
        писать только в Прототип/результаты/, цитата или «общие знания».
Шаг 1. ВХОД: пользователь даёт лист ПА (md/xlsx) или JSON.
        Движок приводит вход к схеме спеки № 1 (JSON). Если данных нет — не выдумывает,
        помечает «домерить» уже на этом шаге.
Шаг 2. ВЫЗОВ ИНСТРУМЕНТА № 1 (ядро):
        python3 узкие_места.py <данные>.json > результаты/отчёт_<дата>.md
        Движок НЕ меняет цифры. Выход ядра — единственный источник чисел.
Шаг 3. ВЫЗОВ ИНСТРУМЕНТА № 2 (retrieval), для каждой находки:
        python3 ИНДЕКС/поиск.py "<термин находки>"
        → берёт 1–2 релевантных источника с документом/страницей.
Шаг 4. РАЗБОР: движок пишет человеческий текст поверх отчёта:
        что значит цифра для потока → тип потери → чего не хватает → цитата источника.
        Граница: НЕ предлагать мероприятия (спека п. 7).
Шаг 5. ВЫХОД: файл результата в Прототип/результаты/ + разбор в чат.
```

## 3. Интерфейсы (все три — один и тот же цикл)

| Интерфейс | Как выглядит для пользователя | Движок | Статус |
|---|---|---|---|
| Чат Kimi + папка «Методички» | «прогони лист ПА» + файл; разбор в ответе | Kimi | **работает сейчас** |
| Терминал | `python3 узкие_места.py данные.json` → отчёт без разбора | нет (Ф1) | готов, для коллег |
| Ollama локально | тот же чат-цикл, endpoint `localhost:11434` | Qwen/Llama | позже; обвязка и файлы — те же |

Смена движка = пересадить роль-файл и два скрипта другой LLM с доступом к Bash. Всё.

## 4. Контракты инструментов

**Инструмент 1 — ядро.** Вход: путь к JSON (схема спеки № 1). Выход: markdown-отчёт в stdout.
Гарантии: детерминизм (3 прогона — пройдено 27.07), все числа с подстановкой в формулу.
Отказ при Тц ≤ 0 / безымянной операции.

**Инструмент 2 — ИНДЕКС.** Вход: строка запроса. Выход: топ-5 документов со сниппетами.
Гарантии: только чтение, покрытие — все 269 документов папки.

## 5. Проверки качества Ф2 (поверх Ф1)

1. Каждое число в разборе = числу из отчёта ядра (движок не пересчитывает).
2. Каждое методическое утверждение — с источником из ИНДЕКСа (документ + страница/раздел)
   или пометкой «общие знания».
3. Разбор не содержит мероприятий. Слова «нужно сделать / внедрить» → стоп, это спека № 2+.
4. Файл результата лежит в `Прототип/результаты/` — больше обвязка никуда не пишет.

## 6. Критерий «Ф2 рабочая»

- 3 прогона на УМД: разбор воспроизводимо содержит верное узкое место, верные цифры
  из ядра и ≥ 1 цитату на находку.
- Первый прогон сдан 27.07 → `результаты/разбор_УМД_2026-07-27.md`.
- Следующий рубеж: реальный лист ПА (задача владельца) → прогон по этому же ранбуку
  без единой правки кода.

## 7. Что осознанно НЕ входит в Ф2

- Автопарсинг произвольных xlsx-листов ПА (форматы у всех разные; пока приведение к JSON —
  шаг движка с глазами владельца). Отдельный парсер — v0.2 вместе с сериями замеров.
- Оркестрация нескольких ролей (L4) — не нужна для одного агента.
- Автономный запуск по расписанию — это Ф3 (Automation).
