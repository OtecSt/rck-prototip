## 1. Две карточки этапа 1 в UI

### Карточка «Пакет ОРД» (инструмент `ord`, этап 1)

Поля формы (JSON-вход режима `ord`):

| Поле | Тип | Обязательность |
|---|---|---|
| предприятие.название / .город | текст | название — желательно; пропуск → «___» |
| приказ.номер / .дата / .нацпроект | текст | пропуск → «___» (нацпроект имеет дефолт) |
| руководитель.должность / .фио | текст | пропуск → «___» |
| ответственные[] {роль, должность, фио, телефон, почта} | список | динамические строки, роли-подсказки из шаблона прил. № 2 |
| поток | текст | подтягивается из карточки проекта (`proekty.поток`) |
| проект.название / .ключевой_риск / .второстепенные_риски[] | текст / список | пропуск → «___» |
| события: старт, диагностика_с/по, совещание, внедрение_с/по, закрытие | даты ДД.ММ.ГГГГ | пропуск → «___»; механика МР-08 — окно 19–28 недель |
| цели[] {наименование, текущий, целевой, идеальный} | список | **заполняется из прогона `smart`** (связка § 3) |
| рамки: клиенты, периметр, границы, владелец, руководитель_проекта, команда[]{фио, должность} | текст / список | пропуск → «___» |

Результат: один docx (раздел 1 — приказ по форме прил. № 2, разрыв страницы,
раздел 2 — карточка проекта) + markdown-отчёт со списком «домерить».

### Карточка «Цели SMART» (инструмент `smart`, этап 1)

Поля формы (JSON-вход режима `smart`):

| Поле | Тип | Примечание |
|---|---|---|
| предприятие.название, поток | текст | подтягиваются из проекта |
| **рамка** | **переключатель**: `федеральная` (дефолт) / `региональная` | +5 %/год (15 % к 3-му) vs +10/15/30 % |
| цели[].наименование | текст | по наименованию автоопределяется показатель МУ-66 (выработка/трудоёмкость/ВПП/запасы) |
| цели[].ед, .текущий, .целевой, .идеальный | текст / числа | пропуск → «___» + «домерить» |
| цели[].срок | дата | T из SMART |
| цели[].горизонт_лет | 1/2/3 | для проверки рамки ПТ (дефолт 1) |
| цели[].методика, .источник, .периодичность, .направление | текст | опциональные переопределения справочника МУ-66 |

Результат: `цели.md` — каждая цель развёрнута по S/M/A/R/T с формулой, источником
данных и периодичностью по МУ-66-2024, флагами валидаторов (измеримость; порог
достижимости 30 %; рамка ПТ) и привязкой к этапам спины. Блок «Домерить» в конце.

## 2. Эндпоинты (добавить в `app.py` по § 4 контракта)

Реестр: `ИНСТРУМЕНТЫ += {"ord": {"этап": 1, "название": "Пакет ОРД"},

Штатный путь прогона — существующий `POST /api/progony` (сервер пересчитывает вход
ядром сам): в `sчитать_itogi` добавить ветки:

- `ord`: `validirovat_ord(вход)` → `gen_ord_docx(вход, путь_к_файлу)` →
  `отчёт_ord(...)` в `отчёт_md`, `итоги_ord(вход, недомеры)` в `итоги_json`.
  **Файл docx**: хранить рядом с БД в `ui/файлы/progon_<id>_орд.docx`; имя файла
  дописать в `итоги_json["файл"]`. Отдельный эндпоинт скачивания:
  **`GET /api/progony/<id>/файл`** → `send_file` (docx).
- `smart`: `validirovat_smart(вход)` → `gen_smart_md(вход)` → md в `отчёт_md`,

Ядро не знает про Flask и БД: все четыре функции принимают/возвращают чистые
dict/str — см. сигнатуры в шапке `ord_smart.py`.

## 3. Связка: цели SMART → карточка проекта → протокол закрытия

1. Пользователь заполняет «Цели SMART» → прогон `smart` сохраняется.
2. На форме «Пакет ОРД» блок «Цели» предлагает **подтянуть последний прогон
   `smart` этого проекта**: `цели[*]` маппятся в таблицу карточки
   (`наименование (+", "+ед)`, `текущий`, `целевой`, `идеальный`).
3. Прогон `ord` сохраняет те же цели в своём `итоги_json.цели` — snapshot,
   как требует доктрина immutable-прогонов.

Формат `итоги_json` (предложение; зафиксировать в § 3 контракта новой редакцией):

```jsonc
// ord
{"предприятие": "...", "поток": "...", "приказ_номер": "...", "приказ_дата": "...",
 "проект": "...", "целей": 3, "файл": "файлы/progon_12_орд.docx",
 "цели": [{"наименование": "ВПП, часов", "текущий": 1179, "целевой": 945,
           "идеальный": 707}],
 "недомеры": ["..."]}

// smart
{"рамка": "федеральная", "предприятие": "...", "поток": "...", "целей": 3,
 "обязательный_показатель_есть": true,
 "цели": [{"наименование": "Выработка, шт. в мес.", "показатель_му66": "выработка",
           "ед": "шт/мес", "текущий": 25, "целевой": 30, "идеальный": 35,
           "дельта_пкт": 20.0, "измеримо": true, "флаги": [], "срок": "16.10.2023"}],
 "недомеры": ["..."]}
```

**Мост в протокол закрытия (задел волны 3):** протокол выполнения мероприятий
(прил. № 6, мер. 0.6 МР-08) должен читать `итоги_json` прогона `smart` (цели и
`дельта_пкт` плана) и прогонов «после» измерительных инструментов (например
`ee`) — сопоставление по `наименование`/`показатель_му66`. Рекомендуемый агрегат
для протокола:

```jsonc
{"цели": [{"наименование": "...", "план_пкт": 20.0, "факт_пкт": null,
           "статус": "ожидает замера «после»", "флаги_плана": []}]}
```

`sravnit_smart(a, b)` (до/после уточнения целей на этапе 2, МУ-65 п. 4.2.4) —
сравнение `цели[*].текущий/целевой/дельта_пкт` по `наименование`, флаг
`частичное` при расхождении состава — в `sravnit()` по общему образцу.
