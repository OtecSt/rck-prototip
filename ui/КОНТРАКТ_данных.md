# КОНТРАКТ ДАННЫХ «Агент-цех» — слой проектов и прогонов (Прогон 4)

> Статус: **ЗАМОРОЖЕН** для волн 2–3. Изменения — только через согласование с владельцем
> и новой редакцией этого файла. Источник истины для всех следующих билдеров.
> Доктрина: прогон = immutable snapshot (вход + отчёт + итоги + автор + дата + комментарий).
> Перезаписи нет: в API отсутствуют UPDATE/DELETE для прогонов.

## 1. БД SQLite

Файл: `ui/agent_ceh.db` (рядом с `app.py`). Движок: stdlib `sqlite3`, без ORM.
Миграция при старте сервера: `CREATE TABLE IF NOT EXISTS` (функция `init_db()`).

## 2. API (Flask, JSON; ошибки всегда `{"ok": false, "errors": [строки]}`)

### `GET /api/proekty` — список проектов
Ответ:
```json
{"ok": true, "proekty": [
  {"id": 1, "название": "ОКЗ пилот", "предприятие": "АО «ОКЗ»",
   "поток": "Производство комбикорма ПК 1-1", "создан": "2026-08-01T12:00:00",
   "комментарий": "", "прогонов": 2}
]}
```
Порядок: новые сверху. `прогонов` — COUNT по проекту.

### `POST /api/proekty` — создать проект
Запрос: `{"название": "...", "предприятие": "...", "поток": "...", "комментарий": "..."}`
(обязательно только `название`). Ответ: `{"ok": true, "id": 1}`. 400 — пустое название.

### `GET /api/proekty/<id>` — проект с прогонами
Ответ:
```json
{"ok": true,
 "proekt": {"id": 1, "название": "...", "предприятие": "...", "поток": "...",
            "создан": "...", "комментарий": "..."},
 "progony": [
   {"id": 3, "этап": 2, "инструмент": "uzkie_mesta",
    "итоги": {"главное_ум": "фасовка", "...": "..."},
    "автор": "РЦК", "дата": "...", "комментарий": "слепой замер", "метка": "до"}
 ]}
```
Прогоны отсортированы по id (хронология). `вход_json` и `отчёт_md` в списке не отдаются.
404 — проект не найден.

### `POST /api/progony` — сохранить прогон
Запрос:
```json
{"id_proekta": 1, "инструмент": "uzkie_mesta",
 "вход": {"операции": [{"имя": "фасовка", "тц_мин": 0.15, "производительность_т_ч": 3.9}], "...": "..."},
 "комментарий": "слепой замер", "метка": "до", "автор": "РЦК"}
```
Сервер **сам пересчитывает вход штатным ядром** (единая точка истины) и сохраняет
снапшот; отчёт/итоги от клиента не принимаются. `метка` вне `до/после` → `''`;
пустой `автор` → `'РЦК'`.
Ответ: `{"ok": true, "id": 3, "итоги": {...}, "отчёт_md": "..."}`.
400 — нет проекта/инструмента, ошибки валидации ядра (возвращаются как есть).

### `POST /api/sravnenie` — дельта-отчёт двух прогонов
Запрос: `{"id_do": 3, "id_posle": 5}` — прогоны **одного инструмента**, порядок задаёт
клиент (ранний → поздний; метки — только подсказка, не валидируются).
Ответ:
```json
{"ok": true, "инструмент": "uzkie_mesta",
 "дельта": { "...структура по инструменту, см. §3..."},
 "дельта_md": "# Сравнение прогонов «до/после» ...",
 "дельта_html": "<h1>...</h1>"}
```
400 — одинаковые id / разные инструменты; 404 — прогон не найден.
Принцип: сравниваются только сопоставимые числа. При расхождении состава данных
`дельта.частичное = true` и в отчёте честно пишется «Сравнение частичное».

## 3. Структура `итоги_json` по инструментам

### `uzkie_mesta` (Поиск узкого места, этап 2)
```json
{
  "главное_ум": "фасовка",
  "подтверждено": true,
  "доли_впп": [["фасовка", 8400.0, 45.0], ["грануляция", 6200.0, 33.2]],
  "ранжирование": ["фасовка", "грануляция", "дозирование"],
  "производительность_т_ч": {"фасовка": 3.9, "грануляция": 9.5455},
  "операции": ["дозирование", "грануляция", "фасовка"]
}
```
- `главное_ум` — имя или `null`; `подтверждено` — сошлись ≥2 детекторов.
- `доли_впп` — список `[имя, сек, доля_пкт]`, отсортирован по убыванию доли.
- `ранжирование` — имена операций по убыванию числа сработавших детекторов (позиция = место).
- `производительность_т_ч` — из входа, только операции с числовым значением.
- `операции` — состав потока (базис сопоставления при сравнении).

**Дельта `uzkie_mesta`** (`дельта` в `/api/sravnenie`):
```json
{"инструмент": "uzkie_mesta", "частичное": false,
 "только_в_до": [], "только_в_после": [],
 "главное_ум": {"до": "фасовка", "после": "грануляция", "изменилось": true},
 "доли_впп": {"фасовка": {"до": 45.0, "после": 20.0, "дельта_пп": -25.0}},
 "производительность_т_ч": {"фасовка": {"до": 3.9, "после": 6.0, "дельта": 2.1, "дельта_пкт": 53.8}},
 "ранжирование": {"фасовка": {"до": 1, "после": 2, "сдвиг": -1}}}
```
Сопоставление операций — **по имени**. `сдвиг > 0` = операция поднялась в рейтинге УМ.
`дельта_пкт = null`, если база «до» нулевая/отсутствует.

### `ee` (ЭЭ-калькулятор, этап 3)
```json
{
  "предприятие": "ООО «НОВОХРОМ»", "поток": "производство дубителя",
  "ээ": 23760000.0, "ээ_пот": 26000000.0, "высвоб": 1500000.0, "налоги": 19000000.0
}
```
Числа — рубли, `null` если ядро не посчитало блок.

**Дельта `ee`**:
```json
{"инструмент": "ee", "частичное": false, "контекст_разный": false,
 "предприятие": {"до": "...", "после": "..."}, "поток": {"до": "...", "после": "..."},
 "числа": {
   "ээ": {"подпись": "Реальный ЭЭ, руб/год", "до": 1.0, "после": 2.0,
          "дельта": 1.0, "дельта_пкт": 100.0},
   "ээ_пот": {...}, "высвоб": {...}, "налоги": {...}}}
```
`частичное/контекст_разный = true`, если различаются предприятие/поток прогонов.

## 4. Регистрация нового инструмента (волны 2–3)

1. Добавить запись в реестр `ИНСТРУМЕНТЫ` в `app.py`:
   `{"ключ": {"этап": N, "название": "Человеческое имя"}}` — ключ попадает в
   `progony.инструмент`, этап — в `progony.этап`.
2. Добавить ветку в `sчитать_itogi(инструмент, вход)`: валидация входа штатным
   валидатором ядра → прогон ядра → `(ошибки, отчёт_md, итоги)`. Итоги — компактные
   ключевые числа + состав данных для сопоставления; зафиксировать структуру в §3.
3. Добавить ветку в `sravnit()` (функция `sravnit_<ключ>(a, b)`): сравнение только
   сопоставимых чисел, флаг `частичное` при расхождении состава.
4. Дописать markdown-секцию дельты в `delta_md()`.
5. В UI: блок истории/сравнения строится тем же кодом, что для UM/ЭЭ (список прогонов
   фильтруется по `инструмент`, итоговая колонка — через функцию `итог(итоги)`).

## 5. UI-контракт (фронт)

- Выбранный проект: `localStorage["agentцех_проект"]` = id проекта (строка).
- Сохранение прогона: фронт собирает вход формы и шлёт `POST /api/progony`;
  отчёт/итоги фронтом не конструируются.
- История: `GET /api/proekty/<id>` → список с чекбоксами; сравнение — ровно два
  отмеченных прогона одного инструмента, «до» = меньший id.

# Приложение. Редакция v1.1 — расширения (фиксы экзамена «Агент-цех», волна 3)

> Базовый контракт выше не изменён. Ниже — только ДОБАВЛЕННЫЕ поля и поведение
> (обратная совместимость сохранена: старые клиенты и старые снапшоты работают).

## Р1. `итоги_json` uzkie_mesta — новые поля (фикс Н4/Н5)

```json
{
  "...прежние поля...": "...",
  "поток": "Производство комбикорма ПК 1-1 или null",
  "детекторы": {"фасовка": ["доля ВПП ≥ 25 %", "мин. производительность (темп)"]}
}
```
`детекторы` — список сработавших детекторов кросс-детектора по каждому кандидату
(из `razbor().кандидаты`). У прогонов, сохранённых до v1.1, поля нет — дельта
об этом честно сообщает.

## Р2. Дельта `uzkie_mesta` (фикс Н5)

- Сопоставление операций — по паре **(имя, порядковый № экземпляра)**; ключи
  словарей `доли_впп`/`производительность_т_ч`/`ранжирование` — `"имя"` для первого
  экземпляра и `"имя #N"` для последующих. Дубли больше не схлопываются.
- Новые поля дельты: `дубли_имён` (список), `пояснение` (текст),
  `почему_ум: {"переехало": bool, "детекторы_доступны": bool,
  "главное_до": {"имя", "детекторы_до", "детекторы_после"}, "главное_после": {...}}`.
- `частичное = true` также при наличии дублей имён.

## Р3. Автоподтяжка протокола (фикс Н3/Н4)

Единая функция `подтяжка_проекта(pid)` (app.py) используется ВСЕМИ путями:
`GET /api/protokol/podtyazhka`, `POST /api/protokol`, `POST /api/progony`
(инструмент protokol). Возвращает `{поля, источники, предупреждения}`:

- `источники.<поле> = {"прогон": id, "дата", "предприятие", "поток"}` —
  пометка источника подтянутого значения (отображается в UI).
- Контекстная сверка: значение подставляется, только если предприятие/поток
  прогона совпадают с карточкой проекта (пустые значения не конфликтуют,
  регистр игнорируется). При несовпадении — значение НЕ подставляется,
  в `предупреждения` добавляется объяснение.
- Подтяжка без `id_proekta` недоступна (400 с подсказкой).
- Ответ `POST /api/progony` для protokol содержит `подтяжка: {источники,
  предупреждения}`.

## Р4. Мост этап 2→3 (фикс Н1)

`GET /api/ee/podtyazhka?id_proekta=N` →
`{"ок": true, "предприятие", "поток", "контекст_диагностики" (главное УМ как
текстовая подсказка с № прогона и датой), "комментарий" (производительности/Тц
операций), "подсказка" (что ввести из экономических данных проекта)}`.
При несовпадении потока прогона с проектом контекст не подставляется
(`подсказка` содержит предупреждение).

## Р5. Чек-лист протокола — по-требовательный ввод (фикс Н6)

Вход ядра протокола расширен: `чеклист.оценки = {номер: {"оценка":
"Соответствует"|"Не соответствует"|"Н/П", "комментарий": "..."}}`.

- Сервер (`баллы_из_оценок`, app.py) вычисляет `чеклист.баллы` по методике
  уровней: уровень N засчитан, если все его требования «Соответствует» или
  «Н/П»; переход к следующему уровню при невыполненном предыдущем запрещён.
  Недооценённое направление в итог не входит (помечается «домерить»).
- Уровни требований — константа `УРОВНИ_ТРЕБОВАНИЙ` (app.py), извлечена из
  официальной формы «Чек-лист оценки 4.0.xlsx»; требование 13.6 (есть только
  в скелете протокола) отнесено к уровню 3.
- При наличии `оценки` docx-таблица прил. № 2 расширяется колонками «Оценка
  требования» и «Комментарий» (форма 132×7); без `оценок` рендер прежний (90×5).
- `GET /api/protokol/skelet` дополнительно отдаёт `trebovaniya`, `urovni`,
  `оценки` для построения формы.

## Р6. Полный снапшот прогона и двусторонняя связка проект ↔ форма (волна 4)

### `GET /api/progony/<id>` — полный прогон (вход + отчёт + итоги)

Ответ:
```json
{"ok": true, "progon": {"id": 9, "id_proekta": 2, "этап": 2, "инструмент": "uzkie_mesta",
  "вход": {...}, "отчёт_md": "...", "итоги": {...},
  "автор": "РЦК", "дата": "...", "комментарий": "...", "метка": "до"}}
```
`вход` и `итоги` — распарсенные JSON-объекты (в отличие от списка
`GET /api/proekty/<id>`, где вход не отдаётся). 404 — прогон не найден.
Снапшот immutable: эндпоинт только читает.

### UI-поведение (слой данных, index.html)

- **Индикатор контекста** (`#pj-context` в шапке): строка
  «Проект: название · предприятие · поток» либо «проект не выбран»;
  обновляется при каждом переключении проекта.
- **Автозагрузка форм**: при выборе проекта для каждого инструмента с прогонами
  последний прогон загружается в форму автоматически, НО только если форма
  «нетронута» (в ней не было пользовательского ввода после последней загрузки/
  сохранения). Если форма редактировалась — в блоке истории показывается
  кнопка-подсказка «Загрузить последний прогон (№ N от дата)», ввод молча
  не затирается. В проекте без прогонов инструмента форма не трогается.
- **Загрузка любой строки истории**: кнопка «→ в форму» в каждой строке таблицы
  истории загружает вход прогона в форму его инструмента и прокручивает
  к карточке (сценарий «замер "после" на базе "до"»).
- **Флаг контекста ввода** (`формаКонтекст[инструмент]`): фиксирует id проекта,
  при котором начат ввод (0 — без выбранного проекта); ставится по первому
  `input/change` с `isTrusted` внутри карточки `.tool[data-tool]`
  (метаполя сохранения, история, ассистент Excel исключены). Сбрасывается
  при загрузке прогона в форму и после успешного сохранения.
  При переключении проекта НЕ сбрасывается — иначе невозможно предупреждение.
- **Защита при saveRun**: если контекст ввода формы отличается от текущего
  проекта — `confirm` «Данные вводились для другого контекста. Сохранить
  в проект «X»?»; отказ отменяет сохранение без блокировки формы.
- Загрузчики форм: УМ/ЭЭ — через `window.__acUM.load` / `__acEE.load`;
  ОРД/SMART/протокол регистрируются через `__acData.registerLoaders({...})`
  (повторная автоподтяжка для карточек, появившихся после слоя данных).

# Приложение. Редакция v1.2 — расширения (фиксы ревизии «Убийца_Ревизор_01», волна 5)

## Р7. Защита от нечисловых данных, строгие id и серверные сверки (У-1…У-12)

### Строгий JSON и конечность чисел (У-1, У-3)
- Все POST-эндпоинты разбирают тело с `parse_constant`: литералы
  `NaN`/`Infinity`/`-Infinity` в JSON — **400** с текстом «не конечное число».
- Дополнительно рекурсивная проверка `math.isfinite` ловит `inf` от переполнения
  (`1e999`): **400** с привязкой к полю.
- Валидаторы ядер (`узкие_места.proverit_vhod`, `ээ_калькулятор._число`,
  `app.validirovat`) требуют конечное число (не bool) для каждого числового поля.
- ЭЭ-калькулятор: после расчёта итоговые суммы (ээ, ээ_пот, высвоб, налоги)
  проверяются на конечность; nan/inf → **400** «результат расчёта — не конечное
  число, проверьте масштаб входных данных» (в `/api/ee_raschet` и в снапшоте).

### Чек-лист протокола: строгая шкала оценок (У-2)
- Значение `чеклист.оценки.<требование>.оценка` — строго одно из
  `«Соответствует» / «Не соответствует» / «Н/П»`. Любая иная строка → **400**
  с номером требования. Неизвестное значение НИКОГДА не засчитывается как
  соответствие. Действует в `POST /api/progony` (protokol) и `POST /api/protokol`.

### Строгие id (У-5)
- `id_proekta`, `id_do`, `id_posle` — `type(x) is int` (bool отклоняется явно).
- Несуществующий проект — **404** (как и ранее).

### Сверка контекста в точке записи (У-6)
- `POST /api/progony`: если предприятие/поток входа непусты и расходятся с
  карточкой проекта — прогон сохраняется, но в ответе поле `предупреждения: […]`,
  а в `итоги_json` фиксируется `"контекст_расходится": true` (immutable-метка).

### Подтяжка протокола: свежесть источника (У-7)
- Источник ЭЭ — самый СВЕЖИЙ ee-прогон по дате; метка «после» — только
  тай-брейкер при равных датах. Если выбранный прогон без метки «после» —
  предупреждение «подставлен замер без пары». В `источники.*` добавлено поле
  `метка`; UI показывает дату и метку подтянутого источника.

### Неположительный ЭЭ в протоколе (У-9)
- ЭЭ ≤ 0: предупреждение в ответе `POST /api/progony` (protokol) и в `отчёт_md`;
  в docx — жирная пометка «ВНИМАНИЕ: экономический эффект неположительный…»;
  у `/api/protokol` заголовок `X-AgentCeh-Warning`. Документ всё равно формируется.
- Отрицательный ЭЭ печатается с типографским минусом: «−500 000 руб. в год».

### Файл прогона (У-8)
- `GET /api/progony/<id>/файл`: путь из `итоги_json.файл` resolve()ится и обязан
  лежать внутри `ui/файлы/` и соответствовать `progon_<id>_(орд|протокол).docx`,
  иначе **404**.

### Потолки и ошибки (У-4, У-10, У-11, У-14)
- `вход_json` прогона ≤ 5 МБ; операций ≤ 500; имя операции ≤ 300 символов — иначе 400.
- `excel_extract`: `data_start` — целое ≥ 1, иначе 400 JSON.
- Любая ошибка БД — JSON **503** `{"ok": false, …}`; при старте — `integrity_check`,
  битая БД = отказ запуска с диагнозом; пустая БД на месте удалённой НЕ создаётся.
- Любой непредвиденный сбой — JSON 500 (не HTML-страница Flask).
- 413: текст зависит от эндпоинта (нейтральный вне загрузки Excel).

### UI (У-12)
- `beforeunload`: если хотя бы одна карточка инструмента «грязная»
  (`формаКонтекст[инструмент] !== undefined`) — браузерное предупреждение
  о несохранённом вводе. Автосохранение черновика в localStorage — задел v1.3.
