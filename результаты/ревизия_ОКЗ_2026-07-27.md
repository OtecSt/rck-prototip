## 1. ЭТАЛОН: что реально нашла и улучшила команда проекта (2022)

Источники: «Протокол выполнения мероприятий ОКЗ.docx» (таблица до/цель/факт), «Презентация день информирования 6 мес.pptx» (слайды 12, 16–18, 29–31, 40).

### 1.1. Узкое место № 1 — участок фасовки
Команда прямо зафиксировала (слайд 12, проблемы № 3 и № 5): «Производительность линии гранулирования ниже линии дозирования» и «Производительность линии фасовки ниже линии дозирования и гранулирования». Эталонный участок выбран именно там: «конечный передел, трудоёмкий передел, низкая производительность по итогам картирования» (слайд 20).
Цифровое доказательство, присутствующее уже в карте текущего состояния:
- производительность: дозирование 15 т/ч → грануляция 9,55 т/ч → **фасовка 3,9 т/ч** (в 3,8 раза ниже дозирования);
- ВПП фасовки = 32 400 сек из 83 765 сек общего ВПП = **38,7 % времени протекания всего потока**;
- итоговый показатель проекта привязан к фасовке: выработка 1,95 → 2,4 т/чел.·ч.

## 2. ОТЧЁТ инструмента vs эталон

Отчёт целиком (15 строк): раздел 1 — «— данных по Тц нет»; раздел 3 «Показатели» — пуст; раздел 4 «Домерить» — спрос и время; раздел 5 — «Узкое место = max(Тц) = "Транспортирующее устройство (после фасовки)" (0,2 мин)». Разделы спеки «Базовые параметры», «Ранжированный список» (наполненный), «ВПП и доля ценности», «Показатели по точечным замерам» отсутствуют.

### (а) Узкое место № 1 — **FAIL**
Инструмент назвал «Транспортирующее устройство (после фасовки)» с Тц = 0,2 мин. Эталонное узкое место — **фасовка**. Формально 0,2 — это max из Тц во входе, но:
- разрыв с фасовкой (0,195 мин) — 2,5 %, в пределах точности замеров; выбор «победителя» на таком зазоре без анализа — шум, а не диагноз;
- главное: во входе в **структурированном** поле `точечные_замеры` лежат производительности 15 / 9,5455 / 3,9 т/ч — фасовка в 3,8 раза медленнее дозирования. Инструмент это поле прочитал (оно в схеме спеки) и **не использовал**. Сигнал эталонного узкого места был в данных — логика его проигнорировала.

### (б) Ранжирование — **FAIL**
Ранжированного списка нет: раздел 1 пуст, в разделе 5 — единственная строка. Эталон ожидал минимум: фасовка → грануляция (перегрануляция 30 %) → дозирование → весовой контроль/транспорт. Инструмент не построил даже тривиальное ранжирование по убыванию Тц, хотя все 11 Тц во входе есть.

### (в) Доказательства цифрами — **FAIL**
Единственная цифра-доказательство — «max(Тц) = 0,2 мин». Не посчитано ничего из того, что считается по имеющемуся входу без «домерить»:
- ΣТц по 11 операциям (≈ 1,32 мин) — не посчитана, раздел «Базовые параметры» отсутствует;
- доли Тц операций в ΣТц — не посчитаны;
- производительности из точечных замеров не сопоставлены;
- замеры спагетти (626 сек / 165 м перемещений — 0,75 % к ВПП, но отдельный сигнал) не использованы.
По спеке (п. 3, раздел 7) «каждая цифра с подстановкой в формулу» — подстановка есть только у одной строки.

### (г) Внутренняя противоречивость — **FAIL**
1. Раздел 1: «данных по Тц нет» — при том что Тц есть у всех 11 операций входа, и раздел 5 тут же находит узкое место по max(Тц). Прямое самопротиворечие, это **баг шаблона отчёта** (вероятно, ветка «нет Тт» ошибочно печатает «нет Тц»).
2. Инструмент объявил узкое место, хотя по спеке узкое место = max(Тц) **при условии Тц > Тт**, а Тт не вычислен (нет спроса/времени). Честный вывод по его же правилам: «кандидат по max Тц — транспортёр/фасовка, подтверждение требует Тт — домерить». Вместо этого — безусловный вердикт.
3. Нумерация разделов дырявая (1 → 3 → 4 → 5), раздел 3 «Показатели» пуст.

### (д) Что инструмент не смог посчитать и почему — **PARTIAL (ближе к PASS по честности)**
Корректно помечено «домерить»: спрос и доступное время → Тт (а через него дисбаланс, N рабочих мест, ВПП тактового потока). Запасы в деньгах и реализация null → оборачиваемость не выдумана. Проверка качества «не выдумывать цифры» (спека п. 5.3) соблюдена — это главный плюс прогона.
Но список «домерить» неполон (запасы перед операциями не упомянуты, хотя это блокер ВПП общего и доли ценности), и, главное, инструмент не посчитал то, на что данных **хватало** (ΣТц, ранжирование по Тц, сопоставление производительностей) — «домерить» использовано как зонтик для полного простоя.

## 3. ПРИЧИНЫ РАСХОЖДЕНИЙ — три класса

### Класс 1. Неполный слепой вход (не вина инструмента)
- `спрос_шт_в_период` = null, `доступное_время_мин` = null → Тт, дисбаланс, N, ВПП тактового потока не вычислимы в принципе. Единой цифры спроса в разрешённых документах действительно нет (только поквартальный АВС без итога).
- `запасы_деньги` = null → оборачиваемость не вычислима (хотя эталон мерил её в днях по складу — вопрос к полноте выборки: данные по запасам склада в карте были, но в JSON не попали).
- `запас_перед_шт` = null по всем операциям → Тож и ВПП общий по формуле 5.1–5.2 не собрать.
Оценка класса: блокирует ~40 % выхода спеки. Слепая выборка честно отразила реальные дыры карты, но и отрезала часть доступного (запасы склада, итоговая выработка).

### Класс 2. Логика инструмента не покрывает случай (вина спеки/алгоритма)
1. **max(Тц) как единственный детектор узкого места — методологически слеп.** В реальной карте ОКЗ Тц смешаны по единицам: блочные Тц (партия 35 т) и поколонные Тц (мешок 30 кг, один замер на колонку). Сравнение их напрямую даёт артефакт «транспортёр 12 сек — узкое место». В спеке нет правила нормализации единиц и нет проверки «единицы потока разные — предупредить».
2. **Производительности из `точечные_замеры` не участвуют в поиске узкого места.** По спеке точечные замеры идут только в раздел «выработка». А именно min(производительность) = фасовка 3,9 т/ч и был эталонным ответом. Нужно правило: «если по операциям есть производительности — узкое место = min, кросс-чек с max(Тц)».
3. **Нет анализа доли ВПП по блокам.** ВПП блоков (8 400 / 13 200 / 32 400 сек) есть во входе текстом в `примечание` — недоступно детерминированному парсеру. Но даже структурно спека не умеет «доля этапа в ВПП» — а это второй по силе сигнал эталона (фасовка = 38,7 % ВПП).
4. **Текстовые сигналы не читаются** (30 % перегрануляция, ожидание грузчика 5 сек). Для детерминированной Ф1 это допустимо, но входной контракт должен был вынести их в поля (`переделка_доля`, `ожидание_сек`), иначе половина карты теряется.
5. **Спагетти-замеры поданы в `точечные_замеры` и проигнорированы** — нет правила для потерь на транспортировку (626 сек / 165 м).

### Класс 3. Баги отчёта
1. «— данных по Тц нет» при наличии Тц у всех операций — ложное сообщение (перепутана ветка Тт/Тц).
2. Узкое место объявлено без выполнения условия Тц > Тт и без оговорки о неподтверждённости.
3. Отсутствуют обязательные разделы структуры спеки: «Базовые параметры» (ΣТц посчитать можно было!), «Ранжированный список» наполненный, «ВПП и доля ценности», «Показатели по замерам». Пустой раздел «3. Показатели» без содержимого.
4. Дырявая нумерация разделов.

## ОБЩИЙ ВЕРДИКТ: **FAIL** (с оговоркой)

Инструмент на реальных слепых данных не нашёл эталонное узкое место, не построил ранжирование и выдал внутренне противоречивый отчёт с багами. Единственное, что работает как задумано, — дисциплина «не выдумывать»: где данных нет, он честно молчит.

При этом расклад виновности примерно такой:
- **~35 % — класс 1** (слепой вход без спроса/времени/запасов — Тт-блок не вычислим никем);
- **~45 % — класс 2** (логика max(Тц) не видит производительности, доли ВПП, смешение единиц и текстовые сигналы — именно то, чем жила реальная диагностика ОКЗ);
- **~20 % — класс 3** (баги: ложное «нет Тц», безусловный вердикт, недостающие разделы, непосчитанный ΣТц).

Вывод для развития: прежде чем обворачивать LLM (Ф2), ядру нужны (1) кросс-детектор узкого места по производительности и доле ВПП, (2) контроль единиц измерения Тц, (3) расширение входного контракта (переделка, ожидание, транспорт, запасы в натуральных единицах), (4) фикс шаблона отчёта и обязательный блок «что посчитано из доступного».
