## 1. Журнал прогона по шагам

### Проект 1 — ОКЗ (проект № 2)

**Шаг 1.1. Создание проекта**
`POST /api/proekty` → `{"ok":true,"id":2}`. Оценка: штатно.

**Шаг 1.2. Превью реального Excel КПСЦ**
`POST /api/excel_preview` (файл `проеткы/ОКЗ/.../Текущая карта  ОКЗ.xlsx`, 81 КБ) → ok, токен, 1 лист «Карта текущего состояния», координаты A1, объединённые ячейки подсвечены. Оценка: штатно, соответствует ЭКСТРАКТОР_ПА_решения.md.

**Шаг 1.3. Извлечение по разметке документа** (orientation=cols; name=15, ВПП=21, Тц=22 сек, произв.=25; диапазон 3–32)
`POST /api/excel_extract` → **11 операций, 1:1 с документом экстрактора**: все Тц (после /60), все ВПП (8400/13200/32400/6000/8050/4410/4200/1855/5250), производительности 15 / 9,5455 / 3,9. 19 подопераций честно пропущены с предупреждениями «нет чисел — пропущено». `возврат_пкт=30` по грануляции не извлекается (текст в списке проблем) — внесён рукой, как и предписано. Оценка: **штатно, эталон подтверждён**.

**Шаг 1.4. Расчёт + прогон «до»**
`POST /api/raschet` → главное УМ «Фасовка в мешок 30 кг.», **ВПП 32 400 сек = 38,7 % — точное совпадение с эталоном** (`данные_окз_слепой.json`), подтверждено ≥2 детекторами; «домерить»: спрос/такт и запасы/оборачиваемость.
`POST /api/progony` (uzkie_mesta, метка «до») → прогон № 9. Ранжирование: фасовка → грануляция («Накопительный бункер пресов») → дозирование — 1:1 с эталоном по существу. Оценка: **штатно**.

**Шаг 2. ЭЭ (проект 1 → 1б)**
Разведка архива ОКЗ: цены единицы, переменной себестоимости единицы, единого объёма реализации, такта и значений «после» в разрешённых документах **нет** (АВС-анализ — поквартально по номенклатурам без итога; «Пример ОКЗ.xlsx» — черновой ДЦ). Вход ЭЭ-калькулятора из архива ОКЗ **не собирается без выдумывания цифр** → по уставу экзамена перешёл на «проект 1б»: эталонный набор Оренбива.
`GET /api/ee_demo/оренбив` → `POST /api/ee_raschet` → ЭЭ **8 350 501,24 руб.** — точное совпадение с экзаменационным эталоном ядра; потенц. 14 299 652,41. `POST /api/progony` (ee, метка «после») → прогон № 10. Оценка: ядро штатно; **применимость к ОКЗ — находка Н1**.

**Шаг 3. Модель «после» + сравнение**
Второй выбойный аппарат: производительность фасовки 3,9 → 6,0 т/ч, ВПП фасовки 32 400 → 8 000 сек (ниже порога), впп_итого пересчитан связно (59 365 сек). Прогон № 11 (метка «после»).
`POST /api/sravnenie {id_do:9, id_posle:11}` → ok. Дельта: фасовка 38,68 % → 13,48 % (−25,2 п.п.), производительность +53,8 %, остальные доли пересчитаны. **Но**: главное УМ осталось «Фасовка», ранжирование «без изменений» — хотя по доле ВПП фасовка (13,5 %) теперь ниже грануляции (22,2 %). Методологически объяснимо (производительность 6,0 т/ч всё ещё минимальна в потоке — детектор производительности удерживает УМ), но **дельта-отчёт этого не поясняет**: методолог видит «ВПП ушло ниже порога, УМ не переехало» и не получает ответа «почему». Оценка: числа верны, интерпретационная поддержка слабая — находка Н5.

**Шаг 4. SMART**
`GET /api/smart/mu66` → справочник (4 показателя, 2 рамки, порог обоснования 30 %). `POST /api/smart` — 2 цели (выработка 3,9→6,0 т/ч; ВПП 83 765→59 365 сек), федеральная рамка → md с разворотом S/M/A/R/T; флаг «ТРЕБУЕТ ОБОСНОВАНИЯ: 53,8 % > 30 %» — корректно. Прогон № 12. **Недомеры: «предприятие», «поток»** — хотя проект № 2 эти поля знает. Оценка: ядро штатно; стык — находка Н2.

**Шаг 5. Протокол закрытия**
`GET /api/protokol/podtyazhka?id_proekta=2` → подтянулись: предприятие, поток, главное_ум, показатели из SMART (До/Цель), цели_smart, **ээ_руб_год = 8 350 501,24**. Оценка подтяжки — см. находки Н3, Н4.
Два пути формирования протокола дали разный результат:
- `POST /api/progony` (protokol) → прогон № 13, итог **25/21 баллов, порог пройден**, файл `файлы/progon_13_протокол.docx`; **ээ_руб_год = null, в docx строка «ЭЭ составит ___ руб.»** — автоподтяжка в этом пути не работает вообще.
- `POST /api/protokol` (id_proekta=2) → docx, в котором ЭЭ **подтянулся — но равен 8 350 501 руб. от ООО «Оренбив»** (прогон 1б), т.е. чужое предприятие в протоколе ОКЗ.

Сверка структуры сгенерированного docx с подписанным протоколом ОКЗ (`Протокол выполнения мероприятий ОКЗ.docx`, прочитан python-docx):
- Нарративные абзацы и таблицы 0–4 совпадают по составу (место/дата, показатели 6 колонок, проекты, подписанты, мероприятия).
- Таблица мероприятий: сервис выводит **все 34 пункта скелета** (35 строк), подписанный — только актуальные (32 строки).
- Чек-лист: подписанный — **132×8**: уровни 1–3, оценка «Соответствует/Не соответствует» по каждому из ~50 требований + колонка «Комментарий»; сервис — **90×5**: только «Оценка критерия, балл» по направлению, без потребованной детализации и без комментариев. Главное структурное расхождение — находка Н6.
- Шапка нацпроекта — редакция 2022 г. (честно помечено в отчёте прогона).

**Шаг 6. ОРД (независимый экзамен)**
`POST /api/progony` (ord) → прогон № 14, `файлы/progon_14_орд.docx`. Приказ + карточка проекта собраны корректно; 17 «домерить»-полей честно перечислены. Замечания: числа целей в таблице — «1.95», «2.3» (английская точка; в SMART/ЭЭ-отчётах рендер по-русски «1,95»); сообщение недомера «ответственные[i]: должность/ФИО/контакты» звучит, хотя должность и ФИО заданы (не хватает только контактов); цели SMART прогона № 12 в ОРД **не подтягиваются** — ввод дублируется. Находки Н7, Н8.

## 2. Находки по стыкам

**БЛОКЕРЫ** — отсутствуют: полный цикл проходится, числа ядер сходятся с эталонами, потерь сохранённых данных не обнаружено (immutable-снапшоты работают).

**Н1 [ВАЖНО] Применимость ЭЭ-калькулятора к реальному проекту.** Вход спеки № 2 (цена ед., перем. с/с ед., объём реализации, такт, фонд времени до/после) не собирается из архива ОКЗ — в проекте это «не измерялось». Сервис не предлагает моста от результатов этапа 2 (УМ, ВПП, производительности) к входу этапа 3: пользователь должен сам добывать финансовые поля. Для ОКЗ ЭЭ в сервисе посчитать нельзя — только «домерить»-режим с внешними данными. Методологический разрыв между этапами 2 и 3.

**Н2 [ВАЖНО] SMART не подтягивает контекст проекта.** Прогон smart внутри проекта с заполненными «предприятие»/«поток» всё равно требует их вручную (недомеры «предприятие, поток» в итогах прогона № 12). Дублирование ввода на ровном месте; подтяжка есть только у протокола.

**Н3 [ВАЖНО] Два пути протокола — две разные автоподтяжки.** `/api/protokol` (скачивание) подтягивает ЭЭ из проекта; `/api/progony` инструментом protokol (immutable-снапшот в истории проекта) — **не подтягивает ничего**: прогон № 13 сохранён с `ээ_руб_год: null`, в docx «___ руб.», хотя ee-прогон в проекте был. Молчаливая расходимость двух «официальных» путей одного документа.

**Н4 [ВАЖНО] Подтяжка ЭЭ не проверяет контекст.** `подтяжка_проекта` берёт ЭЭ последнего ee-прогона (или метки «после») без сверки предприятия/потока с проектом. В протокол ОКЗ подтянулось «8 350 501 руб.» от Оренбива (проект 1б). В реальной работе — риск чужой цифры в подписываемом документе. Достаточно сравнить `итоги.предприятие` с `proekty.предприятие` и честно отказать/предупредить.

**Н5 [ВАЖНО] Дельта до/после не объясняет «непереезд» УМ и теряет дубли имён.** (а) При ВПП фасовки ниже порога дельта показывает «главное УМ: без изменений, ранжирование: без изменений» без пояснения, что УМ удержан детектором производительности — методологу нужна интерпретация, не только арифметика. (б) В карте ОКЗ две операции с одинаковым именем «Перемещение в магазин готовой продукции»: сопоставление в `sravnit_uzkie` по имени через dict молча схлопывает их в одну строку дельты (5,01→7,07), вторая пара (9,61→…) теряется, при этом `частичное=false`. Молчаливая потеря данных в сравнении.

**Н6 [ВАЖНО] Чек-лист протокола структурно беднее официального.** Подписанные протоколы (ОКЗ 132×8, Кушкуль 132×7) содержат оценку «Соответствует/Не соответствует» по каждому требованию, уровни 1–3 и колонку «Комментарий»; сервис генерирует 90×5 с единственной колонкой «Оценка критерия, балл». Баллы сходятся (22/22, 25=итогу ОКЗ), но документ не воспроизводит обязательную форму оценки — для подписания нужна ручная доработка. Также: сервис выводит все 34 мероприятия скелета (подписанные — 32), таблица проектов — фиксированные колонки вместо динамических под показатели проекта.

**Н7 [ЖЕЛАТЕЛЬНО] Несогласованный рендер чисел.** ОРД таблица целей: «1.95», «2.3», «83765» (точка, без разрядов); SMART/ЭЭ/протокол: «1,95», «83 765». Единый форматтер есть (`_f`/`rub`) — в таблице ОРД не применён.

**Н8 [ЖЕЛАТЕЛЬНО] Нет моста SMART → ОРД.** Цели, уже введённые в прогоне smart, в пакет ОРД (этап 1) вводятся повторно вручную. Так же подпись недомера «ответственные[i]: должность/ФИО/контакты» вводит в заблуждение, когда заданы должность и ФИО (не хватает только контактов).

**Н9 [ЖЕЛАТЕЛЬНО] Покрытие эталонов ЭЭ неполное.** В репозитории есть `данные_ээ_атэна.json`, `данные_ээ_строгонов.json`, но `EE_DEMO` в app.py регистрирует только новохром/оренбив; для Кушкуля эталонного JSON нет вовсе (только xlsm-модель в архиве). Регрессионный контур ЭЭ в UI доступен лишь для 2 из 4 справок.

**Н10 [ЖЕЛАТЕЛЬНО] Дата «УТВЕРЖДАЮ» в карточке ОРД** подставляет текущий год («2026 г.»), а не год из `приказ.дата` — для исторического пакета ОКЗ (2021) получается 2026.
