## Н3/Н4 (критично) — ЗАКРЫТО

- Единая функция `подтяжка_проекта(pid)` (app.py) используется ВСЕМИ путями:
  `GET /api/protokol/podtyazhka` (UI), `POST /api/protokol` (скачивание),
  `POST /api/progony` инструментом protokol (immutable-снапшот). (г) ✔
- (а) Без `id_proekta` подтяжка недоступна: 400 с подсказкой «выберите проект в шапке»;
  в UI кнопка без проекта даёт ту же подсказку.
- (в) Контекстная сверка `_совпадает()`: предприятие/поток прогона vs карточка проекта
  (пустые не конфликтуют, регистр игнорируется). При несовпадении значение НЕ
  подставляется + предупреждение с обеими парами «предприятие / поток».
- (б) Пометка источника: `источники.<поле> = {прогон №, дата, предприятие, поток}`;
  UI выводит «(из прогона № N от дата, предприятие/поток прогона: …)» рядом с
  подтянутым значением; ответ `POST /api/progony` содержит блок `подтяжка`.
- (д) Регрессионный тест на экзаменном проекте № 2 (ОКЗ, ee-прогон № 10 от Оренбива):
  `podtyazhka` → `ээ_руб_год: null` + предупреждение; путь progony → снапшот с
  `ээ_руб_год: null`; путь скачивания → docx со строкой «составит ___ руб.».
  Чужой ЭЭ не подставляется ни по одному пути. ✔
- Позитивный тест (проект № 4, ee-прогон с совпадающим контекстом): оба пути
  подставили ОДИНАКОВО — снапшот `ээ_руб_год: 8350501.24` (источник: прогон № 19),
  docx «…составит 8 350 501 руб. в год». ✔

## Н5 — ЗАКРЫТО

- (а) Блок «Почему главное УМ переехало/НЕ переехало» в дельта-отчёте: детекторы
  старого/нового главного УМ в обоих прогонах + методологическое пояснение
  (кросс-детектор, не одна доля ВПП). В `итоги_json` uzkie_mesta добавлено поле
  `детекторы` (расширение Р1 контракта). У прогонов до v1.1 поля нет — дельта
  честно пишет «доступна только арифметика, пересохраните прогоны».
- (б) Сопоставление по (имя + порядковый № экземпляра): ключи `«имя»`, `«имя #2»`.
  На экзаменных прогонах № 9/11 (карта ОКЗ): обе пары «Перемещение в магазин
  готовой продукции» видны — 9,61→13,56 и 5,01→7,07 (ранее вторая терялась);
  `частичное: true`, `дубли_имён`, пояснение в отчёте. ✔

## Н1 — ЗАКРЫТО (реалистичный минимум)

`GET /api/ee/podtyazhka?id_proekta=N` + кнопка «Контекст диагностики проекта»
в карточке ЭЭ: поток/предприятие проекта, главное УМ как текстовая подсказка
«контекст диагностики» (с № прогона и датой), производительности/Тц операций как
комментарий + явная подсказка «цену, с/с, объём, такт ввести из экономических
данных проекта». При несовпадении потока — отказ с предупреждением. Маппинг,
которого нет в данных, не выдумывался.

## Н6 — ЗАКРЫТО (оба режима)

- По-требовательный ввод: `чеклист.оценки = {номер: {оценка, комментарий}}`,
  значения «Соответствует/Не соответствует/Н/П». Автоподсчёт баллов направлений
  `баллы_из_оценок()` по методике уровней (уровень засчитан при полном выполнении,
  переход через невыполненный запрещён; Н/П не блокирует). Уровни — из официальной
  формы «Чек-лист оценки 4.0.xlsx» (87 требований; 13.6 → ур. 3).
- docx при наличии оценок: таблица прил. № 2 = 90×7 (+ «Оценка требования»,
  «Комментарий»); без оценок — прежние 90×5 байт-в-байт (режим «только баллы»
  сохранён). UI: переключатель режима, строки по требованиям с группировкой
  уровень 1→3, живой автоподсчёт (сервер — единая точка истины при генерации).
- Юнит-проверки: все ур.3 «Не соотв.» → 2×14=28; срыв ур.2 направления 2 → 1;
  все ур.3 «Н/П» → 3. ✔
